**Key conclusions**

1. **The catalog is a parts bin, not a team.** About six files are portable almost whole:
   - Research Synthesist
   - Codebase Onboarding Engineer
   - UI Finish-Gate Reviewer
   - AI-Generated Code Security Auditor
   - Minimal Change Engineer
   - Accessibility Auditor

   Everything else contributes rules, tables or templates to a role we write.
2. **The files that look like the obvious pipeline roles are among the worst to fork:**
   - **Senior Developer and Senior Project Manager:** hard-coded to Laravel/Livewire/FluxUI and `ai/memory-bank/`.
   - **Evidence Collector and Reality Checker:** they call a `./qa-playwright-capture.sh` that does not exist and contradict each
     other on "zero issues".
   - **Agents Orchestrator:** it spawns agents by names that do not exist, and it keeps retry caps in prose.
3. **Recommended core: 12 roles exposed as 14 graph nodes** (§7.1):
   - Lead
   - Repo Cartographer (existing repos)
   - Research Analyst
   - BA
   - Architect
   - Security (design mode and verify mode)
   - Designer (design mode and Visual QA mode)
   - Lead Engineer/PM
   - Engineer
   - QA
   - Spec-Verifier
   - Lookback

   The 12 base files total about 38k tokens as published. A trimmed roster should come in under 25k.
4. **Conditional specialists: 15 tier-1 roles, consolidated from 50 conditional files** (§7.2). Each one is a ≤500-token
   **addendum** by default (zero extra calls). It becomes a reviewer node only when a park-the-task risk rule fires (DB migration,
   auth, payments, secrets, IaC/CI, public API). Stack and domain packs (CMS, Salesforce, mobile, Web3, games, GIS…) come later
   (§7.3).
5. **Write from scratch** (§4):
   - The Spec-Verifier (nothing does a req → test → code trace).
   - Lookback.
   - The Lead's engine-facing behaviour.
   - The planner's task schema (`covers`, `after`, `attributes`, `risk`).
   - The BA's elicitation loop and requirement IDs.
   - The Designer's flows, state matrix and prototype contract.
   - The agency layer (client liaison, change requests against a signed spec, estimates).
6. **Graph-node readiness.** Every core and tier-1 role maps cleanly to a node with typed ports (§6). The fork must remove every
   role-to-role and path reference from prompts, because those are the main source of upstream breakage. Wiring belongs to graph
   config.

## 2. Method and scoring

- **Reading.** Seven parallel reviewers each read their batch of files in full against one shared rubric. I read the main
  core candidates myself: Workflow Architect, Minimal Change Engineer, Evidence Collector, Reality Checker, Senior PM, Software
  Architect, Code Reviewer, AI-Code Auditor, Finish-Gate Reviewer, Research Synthesist, Prompt Engineer, Codebase Onboarding and
  Agents Orchestrator.
- **Deterministic checks.** Scripts covered line and token counts, frontmatter keys, self-name vs `name:` mismatches,
  references to missing scripts and paths, prefix conventions, and risky commands.
- **Criteria (1–5).** (a) actionable rules; (b) stack-agnostic, where "inherent" means the stack *is* the role; (c) structured
  deliverables; (d) verifiable success criteria, not vanity metrics. (e) Context cost is computed from size: ≤1.5k tokens = 5,
  ≤3k = 4, ≤4.5k = 3, ≤6.5k = 2, >6.5k = 1. Tokens are estimated as characters ÷ 4.
- **Overall Q** = round(0.30a + 0.15b + 0.20c + 0.20d + 0.15e). Actionability carries the most weight because rules are what we port.
- **Verdicts:**
  - **CORE** = best base file for an always-on role.
  - **CONDITIONAL** = invoked by a task attribute.
  - **ADVISORY** = manual, on demand.
  - **MERGE-INTO-X** = contributes parts to role X.
  - **SKIP** = not delivery-relevant, or too weak.
- **Reconciliation.** Where reviewers disagreed, I set the final verdict, for example on the Visual QA base and the Engineer base.
- **Caveat.** Scores a–d are LLM judgments, made by several reviewers against one rubric. Treat ±1 as noise. Verdicts matter more
  than the exact numbers.

## 6. Roles as graph nodes (n8n-style configurable flow)

The user wants the flow to be configurable and shown live as an n8n-style node graph. That works only if every role is a node
with **typed input and output ports**, and the engine (not the prompt) decides which edge fires. Five node kinds cover
everything:

| Node kind | What it is | Examples | Costs tokens? |
|---|---|---|---|
| **Agent** | One LLM role invocation with a fixed prompt version; reads input artifacts, writes output artifacts | BA, Architect, Engineer | Yes |
| **Gate** | Deterministic tool run by the engine | build, lint, tests, diff-cover, SAST/SCA/secrets, axe, render matrix, trace-matrix builder | No |
| **Human** | Approval or answer, raised through the Lead chat | Approve spec, Approve architecture + design, Answer escalation | No |
| **Router** | Engine logic on artifact fields | verdict switch (PASS / FAIL / UNVERIFIED), fix-loop counter with cap and no-progress exit, task-attribute switch for conditional specialists | No |
| **Trigger** | Starts a flow | Lead chat message, change request, scheduled Lookback run | No |

Rules this implies for the fork:
- A role prompt never names another role or a file path. It names **port types** only. Wiring is graph config. This
  removes the whole class of broken references found in section 5.
- Every output port carries a JSON-schema-validated artifact. Verdict-bearing ports use one enum:
  `PASS | FAIL | UNVERIFIED` (+ `BLOCKED` for escalations). No HOLD, NEEDS WORK, READY or emoji severities.
- Conditional specialists hang off a Router that reads `task.attributes` (set by the Lead Engineer and by gates such as
  "migration files changed"). Advisory roles are nodes with only a manual trigger.
- One role may expose more than one node, each with its own lean prompt, e.g. Security (design mode / verify mode) and
  Designer (design mode / Visual QA mode). Two lean prompts cost fewer tokens than one prompt that carries both modes.

## 8. Next steps

1. **Define the port schemas first**, before any prompt: `brief`, `spec`, `task`, `findings`, `verdict`, `escalation` and
   `trace_matrix`. The verdict enum (`PASS / FAIL / UNVERIFIED`, plus `BLOCKED`) and severity enum (`critical / high / medium / low`)
   live in the engine.
2. **Write the 14 core node prompts** in the locked-core plus editable shape (≤1.5k + ≤0.5k tokens), from the bases in §7.1.
   The order: Engineer, QA, Security (verify) and Spec-Verifier first, because they decide loop cost. Then BA, Lead Engineer,
   Architect, Designer and Lead.
3. **Build the attribute router.** The Lead Engineer sets `task.attributes`, and gates add signals (migration files changed,
   secret found, IaC touched). The router maps attributes to the tier-1 addenda (§7.2) and, for risk rules, to reviewer nodes.
4. **Pilot for token cost.** Run 3–5 real tasks (one new project, two existing repos) through the default graph and record tokens
   per node. Lookback's first scorecards double as the budget baseline.
5. **Licensing.** agency-agents is MIT. Keep the copyright and permission notice in a `NOTICE` or in the header of each forked prompt.
